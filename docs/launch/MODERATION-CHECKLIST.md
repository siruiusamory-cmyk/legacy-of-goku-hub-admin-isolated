# Maintainer moderation checklist

Use [the maintained policy contract](../moderation.md). LOG-HUB-007 exercised both intake routes locally at main `8157622a08e71364dda986277dd27336ed27f91a`: 26 passing checks, real private-review CLI/Sharp/catalog/static output and local signatures; GitHub permissions and human decisions were simulated. No real listing is approved by that test.

1. Read the submission and metadata/hash-only `validation-report`. Check stable repository/owner IDs and actual team authority. First content always requires explicit review, even for trusted owners. Never open an untrusted project executable. Do not post images in public issue comments or upload review directories.
2. On private storage outside this repository and shared/synced folders, choose a **new** directory. With Node 24 and installed dependencies:

   ```powershell
   $env:GITHUB_REPOSITORY = 'siruiusamory-cmyk/legacy-of-goku-hub'
   node tools/moderation-review.js --issue ISSUE_NUMBER C:\Private-LoG-Review-NEW
   # For an existing repository-root manifest instead:
   node tools/moderation-review.js --repository https://github.com/OWNER/REPO C:\Private-LoG-Review-OTHER-NEW
   ```

   Use actual submission numbers; omit all LOG-HUB-007 fixture preloads. The CLI refuses CI and existing destinations. A missing manifest must use the guided route or a separately authorized upstream manifest addition; launch preparation adds no upstream files.
3. Inspect every normalized image, source artwork when needed, and `review.json`: title, description, game/category/status, canonical links, team representation, release/download, numeric identities, content digest and complete ordered artwork set. Require provenance/rights and suitable content. Technical image validation is not artwork approval or malware scanning. Repository MPL-2.0 metadata does not establish rights to game artwork.
4. Decide approve, hold or reject explicitly. `proposed_policy.decision = approved` is inert proposal text. A first approval must copy the **exact current** reviewed identity/content digest and entire ordered source/output artwork-hash array through a protected policy PR. No labels or issue edits grant authority. Third-party `approved_issue`/`approved_digest`, representative verification, sensitive metadata digest and featured placement are separate decisions. Rerun private review if content changed before approval.
5. Replacement: append only the reviewed new artwork set to the existing identity rule. Preserve original `content_digests`, prior approved sets, representation, approved issue/digest, suspension and all unrelated fields. Diff the whole rule. Hash order is cover then screenshots; both source and normalized SHA-256 matter. Never replace an entire rule with the fresh CLI proposal.
6. Hold/reject: leave the candidate artwork unapproved, record the reason; prior approved content/artwork remains. `decision: review` freezes established updates; it is **not removal**. Use `rejected_issue_numbers` for issue rejection and `blocked_user_ids` for abusive submitters, with GitHub close/lock/report tools as appropriate. A rejected replacement can keep generating notices until its source is corrected.
7. Suspend/delist: use an identity-bound `suspended` rule for temporary public removal or `delisted` until explicit reversal. For inappropriate approved artwork, also remove its set approval. An empty last-listing snapshot requires exact repository/owner/project suspension or delisting for **every** prior identity. Keep recovery history. Rebuild and inspect absence of the project, URLs and assets.
8. Abuse report: users choose **Report project content** from [New issue](https://github.com/siruiusamory-cmyk/legacy-of-goku-hub/issues/new/choose), supplying project/repository URLs and a text explanation, no image attachments. Reports notify maintainers; they neither hide content automatically nor grant approvals. Triage impersonation/rights/privacy and malicious distribution promptly; suspend confirmed harmful content, record the decision and verify removal. For sensitive evidence use the owner's separately agreed private channel; the repository has no private abuse mailbox and public issues are public.
9. After an authorized policy merge, inspect the successful catalog publish, protected receipt, validation report and website artifact; confirm exact expected hashes and counts. Public site updates require the separate deployment gate. Check old public Actions artifacts and prior Pages artifacts/deployments for withdrawn bytes and remove affected public copies manually. Disabling future publication does not unpublish existing Pages content; follow [emergency procedures](DEPLOYMENT.md).

Protection observed November 15: required strict `test`, PRs, administrator enforcement and linear history; zero required approving reviews and no enforced CODEOWNER review, changed by owner during LOG-HUB-005. CODEOWNERS still routes responsibility. Human content review remains the documented publishing requirement; current GitHub settings do not enforce a second human reviewer. Do not describe them as doing so and do not change protection in this milestone.

Helper assessment: a local append-only policy-update helper would materially reduce the known replacement error (dropping original digests/ownership fields). Recommend a separately scoped helper **only if repeated operations justify it**: consume a private review file, require matching repository/owner/project, preserve all fields, deduplicate exact ordered sets, produce a diff and refuse implicit approval/merge. Add negative tests for mismatched identities and dropped fields. Do not build it here; the existing CLI plus this two-file comparison is sufficient for the four initial reviews. No CMS, database or paid moderation service is needed.
